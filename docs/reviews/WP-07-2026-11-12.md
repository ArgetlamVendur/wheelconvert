## Findings

### 1. (Required) Untrusted file content and folder names can still decide the error code and reach the user message
`src/WheelConvert.Converters.Media/MediaConverter.cs:196-228` (`MapFailure`) and the comment at `:230-231`.

`MapFailure` searches all of FFmpeg's stderr for "Unknown encoder '…'" and "Invalid data found". Only the source path is removed first. FFmpeg at `-loglevel info` also prints the file's metadata (title, artist…) and paths in other forms, so text chosen by whoever made the file steers the result. Verified with real FFmpeg 9.0.2 in a scratch test (removed afterwards), converting a silent video to Audio:

| Input | Got | Should be |
|---|---|---|
| title tag `plain` | `Unsupported` "This file has no audio track." | (correct) |
| title tag `Invalid data found` | `CorruptInput` "This file couldn't be read. It may be damaged." | `Unsupported` |
| title tag `Unknown encoder 'pwned'` | `ToolMissing` "Your FFmpeg build lacks the pwned encoder." | `Unsupported` |
| file in a folder named `Invalid data found` | `CorruptInput` | `Unsupported` |

Why it matters: wrong C1 error code, and a word taken from the file appears in the message telling the user their FFmpeg is broken. The PR description and the code comment ("The codec name comes from our own arguments") claim this cannot happen. No file is harmed and nothing is executed, so this is not a C2 violation, but it is the exact case the source-path stripping was meant to close.

Fix (author's choice of detail):
- Accept an "Unknown encoder" name only if it is one of the encoders this converter passes (`libmp3lame`, `aac`, `flac`, `pcm_s16le`, `libvorbis`, `libopus`, `libx264`, `libvpx-vp9`); otherwise fall through.
- Match the phrases only on FFmpeg's own diagnostic lines, not on the input dump: e.g. only the last few non-progress lines, skipping indented metadata lines (`    title : …`), and with the temp output path and the source folder removed as well as the source path.
- Add tests: metadata line containing each phrase, and a folder named like the phrase, must not change the result. Correct the comment at `:230-231`.

### 2. (Needs user decision, not the author's fault) Req. 5 / C1 "log the last stderr lines" is not implemented
`src/WheelConvert.Converters.Media/MediaConverter.cs:156`. On a non-zero exit the stderr is dropped; nothing is logged. The author says so in the code and the PR: the frozen constructor has no `ILog`, and there is no static log in Core. The message correctly contains no stderr. Until this is solved, a failed conversion on the user's PC cannot be diagnosed from the log. Fix: user approves an ADR to pass `ILog` to converters (PR follow-up 2), then the author logs the last 5 non-progress lines. Acceptable as a tracked follow-up if the user agrees; the WP acceptance table should then say req. 5 is partly open.

### 3. (Minor) Timeout mapping is not pinned by a test
`tests/WheelConvert.Converters.Media.Tests/MediaConverterTests.cs:280-288` (`Timeout_is_tool_failed_and_discards_temp`). Removing the `if (result.TimedOut)` branch (`MediaConverter.cs:149-152`) leaves all 76 tests green, because the fake result has exit code -1 and falls into the generic `ToolFailed`. Discard on timeout **is** covered (check C). Fix: also assert the message "FFmpeg took too long and was stopped.", or use exit code 0 with `TimedOut: true` so a missing branch would commit a partial file and fail the test.

### 4. (Minor) Real-FFmpeg tests accept `ToolMissing` for every target
`tests/WheelConvert.Converters.Media.Tests/RealFfmpegTests.cs:134-142`. A regression that wrongly returns `ToolMissing` would pass tests 3 and 9 silently. On this PC all 10 targets really converted (see log above), so today's result is sound. Fix: allow the fallback only for encoders that are optional in common builds (`libmp3lame`, `libvorbis`, `libopus`, `libx264`, `libvpx-vp9`), never for `flac`, `pcm_s16le`, `aac`, `gif`; or require at least the built-in ones to succeed.

## Findings

### R1. (Required) Untrusted file content can still decide the error code and put "libx264" in the user message
`src/WheelConvert.Converters.Media/MediaConverter.cs:208-249` (`MapFailure`), comments at `:197-198` and `:201-207`.

The new filter assumes attacker text is always indented, path-stripped, or more than 6 lines from the end. That does not hold. Three bypasses, each **verified through the real `MediaConverter.ConvertAsync` with real FFmpeg 9.0.2** (scratch test, removed afterwards):

| # | Input | Got | Should be |
|---|---|---|---|
| 1 | `song.mp3` whose content is the 2-line text `ffconcat version 1.0` / `file Unknown\ encoder\ \'libx264\'`, → FLAC | `ToolMissing` "Your FFmpeg build lacks the libx264 encoder." | `ToolFailed` |
| 1b | same with `file Invalid\ data\ found` | `CorruptInput` | `ToolFailed` (control: `file plain\ name` → `ToolFailed`) |
| 2 | Silent `.mkv` with 500 tags of ~240 characters each repeating `Unknown encoder 'libx264'`, → Audio | `ToolMissing` "Your FFmpeg build lacks the libx264 encoder." | `Unsupported` (no audio track) |
| 2b | same repeating `Invalid data found` | `CorruptInput` | `Unsupported` |
| 3 | Silent `.mkv` named `\uD800 Unknown encoder 'libx264'.mkv` (lone surrogate, legal on NTFS), → Audio | `ToolMissing` "…lacks the libx264 encoder." | `ToolFailed` |

Why each works:
1. FFmpeg detects the format from content, not the extension. Its concat reader prints the file's own text in a **non-indented diagnostic line at the very end**: `[in#0 @ …] Unsafe file name 'Unknown encoder 'libx264''`. The allow-list does not help: the attacker simply writes an allow-listed name.
2. `ProcessRunner` keeps only the last 64 KB of stderr and cuts in the middle of a line. The cut lands inside an indented metadata line, so its remainder **starts at column 0** and is no longer skipped. Only 5 real diagnostic lines follow it (`Stream map '' matches no streams.` … `Error opening output files: Invalid argument`), so it is inside the 6-line window.
3. FFmpeg echoes a name it could not encode as `�`, so the echoed path differs from `sourceFullPath`, nothing is stripped, and `Error opening input file …\� Unknown encoder 'libx264'.mkv.` is one of the last lines. Any other mismatch between the path we pass and the path FFmpeg prints has the same effect.

Also note the margin in the plain no-audio case is zero: real FFmpeg prints exactly 5 lines after `Input #0 … from '<path>':`, so that line is the 6th and is protected only by path stripping.

Why it matters: same as finding 1. Wrong C1 error code, and the user is told their FFmpeg build is broken because of text inside the file. No file is harmed and nothing is executed (not a C2 violation). The comment at `:197-198` ("so the input dump … can't steer the result") is therefore not accurate.

Fix (author's choice of detail; do not rely on position or indentation):
- Match **whole lines of FFmpeg's own shape, anchored at both ends**, instead of searching for a phrase anywhere. Real lines from FFmpeg 9.0.2 on this PC:
  - `[aost#0:0 @ 000001847790b9c0] Unknown encoder 'nosuchenc'`
  - `[in#0 @ 0000016f3ad00f80] Error opening input: Invalid data found when processing input` and `Error opening input files: Invalid data found when processing input`
  - `Stream map '' matches no streams.`

  An anchored pattern such as `^\[aost#\d+:\d+ @ [0-9a-fA-F]+\] Unknown encoder '([A-Za-z0-9_\-]{1,32})'\s*$` cannot be produced by bypasses 1 and 3, because those lines start with a fixed FFmpeg prefix (`[in#0 @ …] Unsafe file name '`, `Error opening input file `).
- When stderr starts with the `[…truncated…]` marker, **drop the first line after it** (it is a partial line of unknown origin). This closes bypass 2.
- Accept the encoder name only if it is the encoder **this conversion asked for** (the `-c:a` / `-c:v` values for the target), not any name in the list.
- Add `MapFailure` tests using the three real tails above (they must give `ToolFailed`, `Unsupported`, `ToolFailed`), keep the existing legitimate-case tests green, and correct the comments.

### R2. (Required) Text inside the file can still produce the specific error "This file has no audio track."
`src/WheelConvert.Converters.Media/MediaConverter.cs:264-265` (the `Any(...)` over a 4-line window), doc comment `:212-216`.

Unlike the other two branches, this one does not check fixed positions: it accepts `Stream map '…' matches no streams.` on **any** of the four lines before the last line. FFmpeg prints a track's *language* tag raw inside `  Stream #0:0(<language>): …`, and a Matroska language tag may contain line breaks (LF, and CR, which .NET's line reader also treats as a line end). So a file can print a complete line of its choice at column 0. If the text after the injected line is `z=`, the rest of FFmpeg's line becomes `z=): Audio: …`, which `MapFailure` drops as a progress line (`:233`), moving the injected line into the window.

Verified through the real `ConvertAsync` with real FFmpeg 9.0.2: an **audio-only** `.mkv` (track language = `x)⏎Stream map '' matches no streams.⏎z=`, no track tags) → GIF. Real stderr tail:

```
  Stream #0:0(x)
Stream map '' matches no streams.
z=): Audio: pcm_s16le, 44100 Hz, mono, s16, 705 kb/s
Output #0, gif, to '…\.~wc-….gif':
[out#0/gif @ 000001953b3226c0] Output file does not contain any stream
Error opening output file …\.~wc-….gif.
Error opening output files: Invalid argument
```

Result: `Unsupported` "This file has no audio track." Should be `ToolFailed`: the file has *only* an audio track, and the same file with extra lines after the injected one gives `ToolFailed`. Same wrong result with CR instead of LF.

Why it matters: a wrong C1 error code chosen by file content, and the doc comment's claims ("which nothing from the file can follow", "the lines just before it must have FFmpeg's own whole-line shapes") do not hold for this branch. The impact is small: fixed message text, nothing from the file is shown, no file is harmed, nothing is executed (not a C2 violation).

Fix (author's choice of detail): treat this branch like the encoder branch and require FFmpeg's whole closing sequence at fixed positions, as really printed (see the real tails earlier in this file):
- `lines[^5]` matches `NoStreamsPattern`
- `lines[^4] == "To ignore this, add a trailing '?' to the map."`
- `lines[^3] == "Failed to set value '0:a:0' for option 'map': Invalid argument"`
- `lines[^2]` starts with `"Error parsing options for output file "`
- last line as now.

FFmpeg prints its own `Error opening output file …` or `Error parsing options for output file …` line at `[^2]`, so a file cannot supply that sequence unless the map really failed. Add tests: the real tail above must give `ToolFailed`; and pin the positions so that checks a2, a3 and a4 each fail a test (e.g. a no-streams line followed by more lines than the real closing sequence, a no-streams tail that does not end in the fixed last line, and an `Unknown encoder` line that is not at `[^4]` or whose prefix differs from the `Error selecting an encoder` line).
