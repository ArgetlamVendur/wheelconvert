## Findings

1. **BLOCKING: the error log contains the full source path (ADR-013).**
   `src/WheelConvert.Converters.Image/ImagesToPdf.cs:207-212` logs `ex.Message` unchanged. Magick puts the full path in its messages. A scratch run of test 6 with a capturing log printed:
   `Images to PDF failed for broken.jpg: MagickCorruptImageErrorException: insufficient image data in file `C:\Users\<user>\AppData\Local\Temp\wc-pdf-test-…\broken.jpg' @ error/jpeg.c/…`
   ADR-013 says paths in these lines must be cut to the file name, because a shared log would show folder names and the Windows user name. The PR description says "no paths", which is wrong.
   Fix: replace the failing input's full path (and its `/` form) with its file name before logging, as `ImageConverter.LogFailure` does (`ImageConverter.cs:258-271`). Add a test: corrupt input → the `ListLog` lines contain `broken.jpg` and do not contain the test folder.

2. **BLOCKING (missing safety test): no test fails if `Discard` is removed.**
   With `output.Discard(temp);` (`ImagesToPdf.cs:93`) deleted, all 65 tests still pass (M8). `SafeOutputWriter.CreateTempPath` only makes up a name. The temp file appears only at `document.Save`, and tests 6 and 7 both stop before that. So "no temp left" is true in those tests whether or not `Discard` runs. A failure after `Save` (in `Commit`, or a cancel between `Save` and `Commit`) is the only case where `Discard` does anything, and nothing tests it.
   Fix: add a test with an output writer whose `Commit` throws (as `FakeUnwritableOutputWriter`/`TrackingOutputWriter` do in `ImageConverterTests`). Expect `OutputFailed` and no `.~wc-*` file left in the folder.

3. **BLOCKING (missing tests): JPEG-85 vs PNG and CMYK→sRGB are not tested.**
   With every image forced down the PNG path (M5), with `JpegQuality` set to 50 (M6), or with the CMYK→sRGB line removed (M7), all tests still pass. These are WP req. 4 and the CMYK gotcha.
   Fix: (a) a JPEG source gives an embedded image with `/Filter /DCTDecode`, and a PNG source gives `/FlateDecode`. (b) For quality, decode the embedded JPEG stream with Magick and check `image.Quality` is 85 (Magick estimates it from the quantisation tables). (c) A CMYK JPEG source gives an embedded image with `/ColorSpace /DeviceRGB`.

4. **Non-blocking (test gap): cancelling between images is not proven.**
   Removing the `ct.ThrowIfCancellationRequested()` inside the loop (`ImagesToPdf.cs:103`, M13) still passes. The check before `Save` (`:108`) catches the cancel. That only happens after all 30 images are decoded, so the "checked between images" part of req. 6 is not tested.
   Fix: in `CancelDuring30Images_NoTempLeft`, also check that progress stopped soon after the cancel (e.g. fewer than 30 reports).

5. **Non-blocking (test gap): "first frame only" is not tested.**
   Removing `FrameIndex = 0, FrameCount = 1` (`ImagesToPdf.cs:148`, M12) still passes. `MagickImage` probably keeps only the first frame anyway, so the setting may make no difference. Still, nothing checks that a multi-frame GIF or TIFF gives one page.
   Fix: add a test where a 3-frame GIF gives a 1-page PDF.

6. **Non-blocking: PDFsharp errors are reported as "Couldn't save".**
   `ImagesToPdf.cs:79` maps any `InvalidOperationException` to `OutputFailed` "Couldn't save the converted file here.". `XImage.FromStream`/`DrawImage` (`:130-132`) run outside `Prepare`'s catch. If PDFsharp rejects an image it prepared, the user gets a misleading "save" message, and nothing is logged.
   Fix: catch PDFsharp failures in `AddPage` around `FromStream`/`DrawImage` and report `CorruptInput`/`Unknown` naming the file, with a log line.

7. **Non-blocking: the branch needs a rebase.**
   The branch is based on `a695592`. `main` is at `a44703e` (#27), and `docs/STATUS.md` conflicts (`git merge-tree` shows a conflict on that file). AGENTS §7: rebase on `main` before review or merge, and keep both STATUS changes.

8. **Observation: the alpha test catches the bug only by crashing the test host.**
   I removed the white flatten (M2b: `ColorAlpha` deleted; M2c: the whole `HasAlpha` block skipped). In both cases the test run **aborted** ("Test Run Aborted", 6 of 65 run) instead of an assertion failing. It still counts as caught. But it means a PNG with alpha that reaches PDFsharp can take down the whole process. In the app that would be the tray app. With the code as written, alpha is always flattened, so this is not a current bug. I did not find the root cause (read only).

## The shared xunit collection

Sound. `ImageConverterTests` changes process-wide `ResourceLimits.Width` (line 694), and `Area`/`Disk` (lines 819-820, set to 1). `ImagesToPdf.Prepare` reads `ResourceLimits.Width/Height`, and Magick reads the same limits on every decode. Running the two classes in parallel can make PDF tests fail at random, which matches the builder's transient "cache resources exhausted". These are the only two test classes in the assembly, so the collection just runs them one after the other. That costs a few seconds and keeps the tests reliable.
