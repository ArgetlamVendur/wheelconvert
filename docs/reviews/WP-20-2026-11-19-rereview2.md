## Verdict: **CHANGES NEEDED**

All findings from re-review 1 are fixed: the RunLength regression (finding 1) and the 500-character cut (finding 2) now have tests that fail when the fix is reverted, and the source-read mapping (finding 3) works. But the new guard `HasDecodableContents` only looks at `/Filter`. It ignores `/DecodeParms`, and PDFsharp 6.2.4 gets that case wrong in two ways when the page-touch loop wraps the contents. Both are regressions from the round-1 page-touch loop. Neither happens with the loop removed. One of them silently damages a page in the output while reporting success.

## Findings

### Blocking

1. **`src/WheelConvert.Converters.Pdf/PdfShrinker.cs:214-225` (guard) with `:117` (touch): a Flate content stream with a predictor in `/DecodeParms` comes out damaged, and the converter still reports success.**
   Scratch test: page 1 has a big JPEG. Page 2's content is `/FlateDecode` with `/DecodeParms << /Predictor 12 /Columns 8 >>`, and its decoded bytes are a grey 50x50 rectangle. The guard accepts it because the filter is Flate. PDFsharp decodes the stream, applying the predictor. On save it re-encodes the stream with plain Flate, but it **keeps `/DecodeParms << /Columns 8 /Predictor 12 >>`**. Readers then apply the predictor to data that was never predicted. PDFium render of page 2: 324 grey pixels before, 36 after, so the drawing is gone. The result is `Success`. The render check only renders page 1, and only checks that it renders, so it can't catch this. The source is untouched (C2 holds), but the user gets a "smaller" PDF with a broken page and no warning. With the touch removed (guard forced false), the same page renders identically (324/324).
   Predictors on content streams are rare (they're normal on images and xref streams), but they are legal PDF.
2. **Same place: `/Filter [/FlateDecode]` with `/DecodeParms [null]` (the normal array form) makes the whole shrink fail with the wrong message.**
   The guard accepts it. The touch throws `InvalidOperationException: 'Byte[]' must not be null here.`, and calling `Save` after that throws `InvalidCastException: GetName: Object is not a name` inside `PdfContent.WriteObject`. In `ShrinkAsync` the `InvalidOperationException` is caught by the outer catch (`:149`), which returns `OutputFailed` "Couldn't save the file here." Nothing is logged, and the message blames the output folder. With the touch removed, the same file shrinks successfully. Temps are discarded and the source is unchanged, so this isn't a safety issue. It's the same kind of regression as re-review 1 finding 1.

   **Fix for 1 and 2 (one change):** in `HasDecodableContents`, return `false` for any content stream that has a `/DecodeParms` entry (`stream.Elements["/DecodeParms"] is not null`), so the page is left untouched, the same as RunLength pages. Add two tests modelled on `Shrink_PageWithRunLengthContent_IsLeftByteIdentical_AndTheRestShrinks`: (a) Flate + `/DecodeParms << /Predictor 12 /Columns 8 >>`, where the content stream must come out byte-identical; (b) `/Filter [/FlateDecode]` + `/DecodeParms [null]`, which must succeed with the stream byte-identical. (For (a), the row data is `0x00` + 8 content bytes per row, Flate-compressed.)

### Non-blocking

3. **`PdfShrinker.cs:74-81`: the new read-error mapping has no test, though a test is easy to write on Windows.** I reverted the catch to `throw;` and all 103 tests passed. A scratch test that holds the source with `new FileStream(source, Open, ReadWrite, FileShare.ReadWrite)` plus `hold.Lock(0, hold.Length)` gets past the open, then fails on the first `ReadAsync` with `IOException`. On the PR code it returns "Couldn't open this PDF. Another app may be using it." with no temps left. With the mutation it returns `OutputFailed` "Couldn't save the file here." So that test would catch the regression. Suggest adding it (Windows-only attribute, or skip it on other platforms).
4. **`docs/STATUS.md:26`: the notes column still describes fix round 1 ("Needs re-review" after round 1).** Cosmetic. Update it when the status next changes.

## The new copy loop (`PdfShrinker.cs:61-90`)
- The source is opened `FileMode.Open, FileAccess.Read, FileShare.ReadWrite | FileShare.Delete`. That's read-only and shared. ✔
- Temp A is opened `FileMode.CreateNew, FileAccess.Write, FileShare.None`. ✔
- Cancellation: the token is passed to both `ReadAsync` and `WriteAsync`. Scratch test with a token cancelled up front: `OperationCanceledException` propagates, and no temp is left (temp A had already been created empty). ✔
- No partial temp on failure: the early `return` inside the loop and any exception both leave through `finally`, which discards temp A (and temp B). Lock-range scratch test: no temp files left. ✔
- Only `IOException`/`UnauthorizedAccessException` from the **read** are mapped to "Couldn't open this PDF". A write error still falls through to the outer `OutputFailed` catch, which is correct.
