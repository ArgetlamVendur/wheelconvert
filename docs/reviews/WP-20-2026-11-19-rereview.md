## Findings

### Blocking

1. **`src/WheelConvert.Converters.Pdf/PdfShrinker.cs:92`: the page-touch loop throws `NotImplementedException` for content streams with a filter PDFsharp 6.2.4 can't decode. The whole shrink fails and nothing is logged.**
   `PdfPage.Contents` wraps each content stream in `PdfContent`, and its constructor calls `Decode()` on the stream. For a filter PDFsharp doesn't implement (tested with `/RunLengthDecode`, a standard PDF filter; I did not list which other filters PDFsharp lacks), this throws `System.NotImplementedException: Filter not implemented: RunLengthDecode` (stack: `Filtering.GetFilter` ← `PdfContent.Decode` ← `PdfContent..ctor` ← `PdfPage.get_Contents` ← `PdfShrinker.cs:92`). `ShrinkAsync`'s outer catch only handles `IOException / UnauthorizedAccessException / InvalidOperationException`, so the exception goes up to `PdfConverter.cs:130`, which returns `Unknown` "Something went wrong while working on this PDF." Temps are still discarded and the source is unchanged, so this is not a safety problem. But:
   - It's a regression from this round. With the loop removed, the same PDF (a 3000×2000 JPEG page plus one RunLength content page) shrinks fine, and the RunLength stream is kept byte-for-byte.
   - It isn't logged, so a user's bug report would show nothing.
   - The exception could also be thrown halfway through building the `PdfContent` wrapper, after PDFsharp has already changed the object's type, so catching it and carrying on with the same document is not obviously safe either.
   **Fix (builder's choice):** before touching a page, check that every stream in its `/Contents` has no filter or only filters PDFsharp decodes (in practice `/FlateDecode`, which is what real files use), and skip the touch for pages that fail the check (their content stays exactly as it is). Or, if the loop throws, give up on content compression and save without the loop by reopening temp A. Add a test: a PDF with a big JPEG page and one `/RunLengthDecode` content page (e.g. bytes `[n-1] + content + [128]`) must shrink successfully, and the RunLength stream must come out byte-identical.

## Page-touch loop: what it can and can't change (asked by the orchestrator)

I added a scratch test (not committed; removed afterwards, tree clean). It builds a PDF with: page 1 = big JPEG + extra drawing + a **web link annotation**; page 2 = drawing + a **text annotation**; **two bookmarks**; page 3 with **no `/Contents`**; page 4 with a single non-array content stream; pages 5-6 **sharing one indirect `/Contents` array**. The test compares each page's decoded content bytes, annotation counts and outline count before and after, and renders every output page with PDFium.
- Page 4 as `/ASCIIHexDecode`: **all equal**, all pages render. Annotations, link, bookmarks and the shared-array pages are kept. The page with no contents stays empty.
- Page 4 as a **truncated** `/FlateDecode` stream: all equal (PDFsharp decodes it the same way before and after), renders.
- Page 4 as `/RunLengthDecode`: **the shrink throws** (finding 1).
- Reading the code: the loop only reads `page.Contents`. In PDFsharp that replaces `/Contents` with a direct array that holds the same stream references, and decodes each stream so it can be re-encoded with Flate on save. It never touches `/Annots`, `/Resources`, the outline tree or the AcroForm. The existing `Shrink_KeepsLinkAndBookmark` test also passes with the loop.

So for decodable content the loop doesn't change page content or lose links, annotations or bookmarks. The only problem is filters PDFsharp can't decode.
