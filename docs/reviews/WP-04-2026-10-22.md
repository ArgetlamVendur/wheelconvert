### Check 6: Positioning & Deliberate Deviation Evaluation
- **Status:** **PASS**
- **References:** [WheelWindow.xaml.cs:136-165](file:///src/WheelConvert.App/Wheel/WheelWindow.xaml.cs#L136-L165)
- **Evaluation:**
  - **Deliberate Deviation:** `PlaceAt(ScreenPoint point)` positions the window in physical pixels via `SetWindowPos` instead of setting WPF's `Window.Left` and `Window.Top` in DIPs.
  - **Verdict:** **APPROVED**.
  - **Rationale:** WPF converts `Left`/`Top` using the DPI of the monitor where the window *currently* resides. If a drag or hotkey occurs on a secondary monitor with a different scaling factor, setting `Left`/`Top` in DIPs causes WPF to scale by the wrong monitor's factor, displacing the window. Using `MonitorFromPoint` to find the target monitor, querying effective DPI via `GetDpiForMonitor`, and centering via Win32 `SetWindowPos` in physical coordinates ensures pinpoint placement. Clamping against `info.rcWork` with `Math.Max(work.Left, Math.Min(point.X - (size / 2), work.Right - size))` and `Math.Max(work.Top, Math.Min(point.Y - (size / 2), work.Bottom - size))` keeps the wheel fully within the monitor's work area on all edges. Calling `SetWindowPos` twice ensures that if WPF handles `WM_DPICHANGED` across monitors, the final physical coordinate is exact.

### Check 8: In-Progress Drag Lifetime and Deferred Hide
- **Status:** **PASS**
- **References:** [WheelWindow.xaml.cs:86-111](file:///src/WheelConvert.App/Wheel/WheelWindow.xaml.cs#L86-L111), [WheelWindow.xaml.cs:225-245](file:///src/WheelConvert.App/Wheel/WheelWindow.xaml.cs#L225-L245), [WheelWindow.xaml.cs:247-270](file:///src/WheelConvert.App/Wheel/WheelWindow.xaml.cs#L247-L270)
- **Evaluation:** When `HideWheel()` is invoked while `_dragInProgress == true` (such as when a mouse-up trigger dismiss arrives milliseconds before Explorer delivers the drop event), the wheel sets `_hidePending = true` and starts a 2-second `_pendingHideTimer`. Crucially, the window remains visible (`IsOpen` reports false, but `Hide()` is not called and opacity is not altered) because Windows does not deliver drops to fully transparent or hidden windows. Once `OnDrop` or `OnDragLeave` executes, `HideNow()` is called to cleanly dismiss the window and reset state. If neither arrives within 2 seconds, the backstop timer calls `HideNow()`.

## 4. Numbered Findings

There are **0 blocking or safety findings**. The following minor non-blocking note is recorded:

1. **`src/WheelConvert.App/Wheel/WheelWindow.xaml.cs:225-245`**
   - **Why:** `OnDragEnter`, `OnDragOver`, and `OnDrop` explicitly assign `e.Effects = DragDropEffects.Copy` on entry and constrain `e.Effects` to `Copy` or `None` in `finally`. `OnDragLeave` sets `e.Handled = true` in `finally`, but does not explicitly assign `e.Effects = DragDropEffects.None`. While Win32 OLE `IDropTarget::DragLeave` does not communicate a drop effect back to Explorer, setting `e.Effects = DragDropEffects.None` inside `OnDragLeave` provides additional defense-in-depth within WPF's internal routed event handling.
   - **Fix:** Non-blocking minor polish: When editing this file in future maintenance, add `e.Effects = DragDropEffects.None;` inside `OnDragLeave` before or within its `finally` block for consistency.
