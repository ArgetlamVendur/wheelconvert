## 1. Evaluation of Deliberate Deviations

The builder's PR description lists 4 deliberate deviations from `docs/modules/WP-11-integration.md`. Each has been evaluated:

1. **No "Starting…" wheel state (req. 1)**
   - **Verdict:** **APPROVED**
   - **Rationale:** `IWheelView` is a frozen contract (`docs/CONTRACTS.md` C4, `AGENTS.md` §4.1) and provides no API to display a loading or starting state. In addition, the frozen `TrayIcon` constructor requires a constructed `FormatRegistry`. Offloading registry creation and converter health checks to a worker thread via `Task.Run` in `CompositionRoot.BuildAsync` avoids blocking the UI thread (~0.6 s start-up time) and ensures the wheel, tray, and triggers are only instantiated once the registry is ready, making an early trigger impossible.

2. **Shutdown order (req. 11): Tray disposed before queue drain**
   - **Verdict:** **APPROVED**
   - **Rationale:** `App.OnExit` synchronously blocks the UI thread on `AppHost.DisposeAsync()`. `NotifyIcon` is a WinForms object with strict UI thread affinity; disposing it after an asynchronous await (`await _queue.DisposeAsync()`) while the UI thread is blocked would result in thread-affinity violations or deadlocks. Disposing UI objects (`_triggers`, `_wheel`, `_tray`) before the first await—after calling `_coordinator.Stop()` to ensure no background completion notifications reach the UI—is architecturally correct. The 4-second timeout on the queue drain ensures the entire shutdown finishes well within the 5-second limit.

3. **Constructor changes to WP-11-owned `AppHost` and `CompositionRoot.BuildAsync`**
   - **Verdict:** **APPROVED**
   - **Rationale:** `AppHost`, `CompositionRoot`, and `App.xaml.cs` are owned by WP-11 and are not part of the frozen core contracts or called by other modules. All constructors of types owned by other work packages (`TrayIcon`, `PageOrderPrompt`, `WheelWindow`, `PdfPageRenderer`, converters) were left untouched. `BuildAsync(Dispatcher, ILog)` is required for the async start-up sequence. The builder correctly documented the proposal in the PR description per `AGENTS.md` §4.1.

4. **Fallback notification shown on every trigger apply**
   - **Verdict:** **APPROVED**
   - **Rationale:** When the user switches trigger modes via the tray during an active session, re-evaluating the trigger and notifying immediately if Shift-drag fails provides necessary feedback explaining why the selected mode could not start and that hotkey fallback was applied. Combining failures into a single Error notification when both triggers fail prevents notification noise.

## 3. Numbered Findings

There are **0 blocking or major findings**. The following non-blocking findings and notes are recorded for follow-up:

1. **`src/WheelConvert.App/Composition/TriggerManager.cs:189`**  
   - **Why:** `OnLivenessTimerTick` checks `DateTime.UtcNow - shiftDrag.LastActivityUtc < HookSilenceLimit`. If `ShiftDragTrigger.Start()` in WP-02 does not reset `LastActivityUtc` upon start/restart, an idle mouse with active keyboard input will cause the liveness check to reinstall the hook every 60 seconds and log each time.  
   - **Fix:** Follow-up for WP-02: Ensure `ShiftDragTrigger.Start()` explicitly sets `LastActivityUtc = DateTime.UtcNow`.

2. **`src/WheelConvert.App/Composition/DropCoordinator.cs:129`**  
   - **Why:** `j.Result!.Success` uses null-suppression `!` without an inline comment directly on line 129 (`AGENTS.md` §6: "no `!` suppressions without a comment why"). The overarching invariant is documented on line 128 (`// Result is non-null: filtered above.`) because `jobs` is filtered at line 120 with `j.Result is { Error: not ConversionError.Cancelled }`.  
   - **Fix:** Non-blocking minor polish: When touching this file in future maintenance, pattern-match `j.Result is { Success: false }` or add inline comments so static analyzers and linters don't flag the line independently.
