## Findings (all non-blocking)

1. **`src/WheelConvert.App/Tray/TrayIcon.cs:145`, `:277`, `:81-88`, `:103-104`, `:118`: no test protects the TrayIcon rules.**
   Why: AGENTS §2 asks that each safety rule fail a test when reverted, or that the review says why it can't be tested. I removed each of these in turn and all 87 tests still passed: the existence check before reveal, the existence check before opening the settings/log file, the dispatcher marshal in `Notify`, the `NotifyIcon` hide + dispose, and the `ShouldShow` call. Reason they are untested: they need a live `NotifyIcon` on an STA thread and would launch Explorer. That is only partly a good reason.
   Fix (author, follow-up is acceptable): move the "may this path be revealed/opened?" decision into a pure function (path + an exists-check delegate) and test it for missing, relative and existing paths. Optionally add one STA test that constructs and disposes `TrayIcon` and calls `Notify` from a worker thread, like the WP-03 hotkey test does.

2. **`src/WheelConvert.App/Tray/TrayIcon.cs:152`: reveal selects the wrong thing when the full path has a comma and no space.**
   Why: .NET only quotes an argument that contains a space or a quote, so the command line becomes `explorer.exe /select, C:\dir\a,b.txt`, and Explorer treats the comma as a separator. Confirmed by running the same command line on scratch files: `plain.txt` opened its folder with the file selected; `a,b.txt` opened `OneDrive` with "Documents" selected. No file is touched; the user just lands in the wrong folder. Paths with a space anywhere (for example under `D:\Claude Base\`) are quoted and work.
   Fix: this is the spec's own form (req. 2), so it is a spec question for the user, not an author error. The reliable form is a single raw argument string `/select,"<path>"`, which the spec's "ArgumentList only" wording does not allow today. Decide in WP-11 or a small follow-up; if changed, the path must still be validated as it is now.

3. **`tests/WheelConvert.App.Tests/TrayMenuModelTests.cs:82`, `:144`, `:163`: the length-limit tests compare against the constants they are meant to check.**
   Why: changing `MaxTooltipLength` to 64 or `MaxUserTextLength` to 200 leaves every test green. Harmless today (the tooltip is a 12-character constant), but the tests would not catch a wrong limit.
   Fix: assert the literals `63` and `120` once (for example `Assert.Equal(63, TrayMenuModel.MaxTooltipLength)`).

4. **`src/WheelConvert.App/Tray/TrayIcon.cs:213`: old Status submenu items are dropped without `Dispose` every time the menu opens.**
   Why: `DropDownItems.Clear()` does not dispose the removed `ToolStripMenuItem`s (and the "Check again" click handler). Small, slow leak in a long-running tray app; no functional effect.
   Fix: dispose the removed items after clearing, or build the fixed items once and only update the status lines.

5. **`src/WheelConvert.App/Tray/TrayMenuModel.cs:75-86` and `TrayIcon.cs:161`: two deviations from the spec that I can't confirm were approved.**
   Why: req. 3 gives a fixed "How to use" sentence; the code shows a different sentence per trigger mode, and shows it even when success notifications are off. Both are sensible (the fixed sentence would mention a hotkey that is off in the default mode) and the PR description says the user approved them before the build. This session has no record of that approval. Same for the new test file outside the Owns list, which also holds a second public class (`StartupRegistrationTests`), against "one public type per file" (AGENTS §6).
   Fix: user confirms the approval when merging; nothing for the author to change. Updating req. 3 in the WP file to match would keep the spec honest.

6. **`src/WheelConvert.App/Tray/TrayIcon.cs:152`, `:283`: `explorer.exe` is found by Windows' search order, not by full path.**
   Why: with no shell, Windows looks in the app's own folder first, so a file named `explorer.exe` placed next to `WheelConvert.exe` would run instead. Anyone who can write there can already replace the app, so the risk is low, and the bare name is what the spec prescribes.
   Fix (optional hardening, follow-up): build the path from `Environment.GetFolderPath(Environment.SpecialFolder.Windows)`.

Nits, no action needed for approval: `docs/STATUS.md` PR column says `wp-05-tray` instead of `PR #11`; the trigger items show a tick rather than a radio dot (cosmetic, see user test 3).

## For the user before merging

1. Start the app: a blue wheel icon appears in the tray; hovering shows "WheelConvert".
2. Right-click it: header with version, "How to use", Status, Trigger (Shift-drag / Hotkey / Both), "Start with Windows", "Open settings file", "Open log", Exit.
3. Tick "Start with Windows", open `regedit` → `HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\Run`: a value `WheelConvert` with the exe path in quotes. Untick it: the value is gone.
4. Choose Exit: the icon disappears at once, without hovering over it.
5. Confirm (or reject) the deviations in finding 5.
