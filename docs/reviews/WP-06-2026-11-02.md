### 1. BLOCKER: policy does not deny SVG or `text:` (`ImageConverter.cs:258-290`)
- **Why:** The policy is applied through `ConfigurationFiles.Default.Policy.Data` and `MagickNET.Initialize(configFiles)`, not the `MagickNET.SetSecurityPolicy` that req. 4 names. The deviation is not noted in the code or the PR as a deviation (AGENTS §4 rule 12). I probed it after the static constructor ran, reading each file with an explicit format:
  - `MagickFormat.Mvg` is blocked (`MagickPolicyErrorException ... security policy 'MVG'`).
  - **`MagickFormat.Svg` is read successfully** (10×10 image returned).
  - **`new MagickImage("text:<path>")` is read successfully** (612-px render of the file's text).
  - So two of the ten denied coders (SVG, TEXT) are not denied. I did not test the other seven and did not find the root cause. A guess is that the SVG and text readers run under a different coder name than the pattern, but I haven't confirmed it.
- **Real-world impact today:** Limited. Every read passes an explicit extension-derived `Format`, and my probe confirmed that SVG, MSL, MVG and plain text hidden in `.png`/`.jpg` files are all refused as `CorruptInput` with no new files. So the guard that actually works is format forcing. The policy is the second layer the spec asks for (checklist line 9 says both), and that layer has a hole.
- **Fix:** Make the policy actually enforce every coder in the req. 4 list. Try `MagickNET.SetSecurityPolicy` as the spec says, or fix the patterns. Then prove it with a test (finding 2). If the spec's call can't work, say so in the PR under rule 12.

### 2. MAJOR: test 7a proves nothing about reads (`ImageConverterTests.cs:262-289`, payload at `:271`)
- **Why:**
  - The payload references `'file.txt'` by a relative path. ImageMagick resolves that against the process working directory, not `_testDir`, so a successful read could never have found the file. The test would pass even with no protection.
  - `Assert.Equal(secretContent, secretAfter)` (`:283-284`) only shows the file is unchanged. Reading does not change a file, so it cannot show "not read".
  - The test passes only because the PNG decoder rejects the text. It never exercises the security policy at all, which is why finding 1 went unnoticed.
  - The WP table records 7a as PASS with "`file.txt` not read" as the expected result, so that PASS is not supported.
- **Fix:**
  1. Use an absolute path to a file whose content would show up in the output. For example, a secret image the MVG would composite in, then check the output doesn't contain it.
  2. Add policy tests that read a tiny valid MVG, SVG and `text:` input with an explicit format, and expect `MagickPolicyErrorException`.
  3. Keep the folder-listing assertion (`:287-288`), which is fine.

### 3. MAJOR: write failures mapped to `CorruptInput` (`ImageConverter.cs:143-146`)
- **Why:** WP-06 req. 5 and CONTRACTS C1 say a folder-not-writable or disk-full case is `OutputFailed`. Magick write errors surface as `MagickException` subtypes, not `IOException`, so they fall into the generic `catch (MagickException)` and become `CorruptInput` with the message "Failed to decode or process image." I confirmed this with a fake `IOutputWriter` whose temp path pointed at a non-existent folder: the result was `CorruptInput`, not `OutputFailed`. A user dropping a photo into a read-only folder would be told the photo is damaged.
- Related at `:147`: a plain `IOException` while reading the source (file locked) is also reported as `OutputFailed`.
- **Fix:** Separate read and write failures. For example, wrap the `Write` calls (or catch `MagickBlobErrorException` / file-open errors) so they return `OutputFailed`. Add a test with a writer that returns an unwritable temp path.

### 4. MINOR: static constructor can crash or hide a failed policy (`:36-39`, `:286-289`)
- **Why:** `Initialize(configFiles)` writes config files to a temp folder. An `IOException` or similar there is not in the catch list, so it becomes a `TypeInitializationException` thrown from `new ImageConverter()`, which would stop the app at composition rather than letting `CheckHealth()` report `Missing`. The caught exceptions are swallowed with no record that the policy and limits were not applied, while `CheckHealth()` still says `Ready`.
- **Fix:** Record the failure in a static field and have `CheckHealth()` return `Missing` if limits or policy were not applied. Catch all exceptions in the initialiser. The converter should not run unprotected.

### 5. MINOR: `InvalidOperationException` thrown before the `try` (`:103-104`)
- **Why:** CONTRACTS C1 says `ConvertAsync` never throws except `OperationCanceledException`. A target without an extension throws here. Unlikely for the four image targets, but it is a contract breach and the cheap fix is a `Fail(Unsupported, ...)`.
- **Fix:** Return `ConversionResult.Fail(ConversionError.Unsupported, ...)`.

### 6. MINOR: ADR-010 row incomplete for WP-12 (`ADR-010-package-versions.md`)
- **Why:** ADR-005 says WP-12 compiles `THIRD-PARTY-NOTICES.md` from ADR-010. The row lists 13 native libraries; the full list of ~38 (libraw, librsvg, cairo, glib, pango, fribidi, lqr, and others, several LGPL) exists only in the PR description. Spot-checks against the package `Notice.txt` matched (libheif and libde265 are LGPL, libraw and librsvg are present). I did not verify every version number or licence line.
- **Fix:** Put the full table in ADR-010 or link to a file under `docs/`. I'd also ask WP-12 to check whether these LGPL delegates are statically linked into the Magick native DLL, since ADR-005's "LGPL notices required" may not be enough then. I did not verify this.

### 7. MINOR: cancellation test is trivial (`ImageConverterTests.cs:240-260`)
- **Why:** The token is cancelled before `ConvertAsync`, which throws at line 85, before `CreateTempPath`. No temp is ever created, so the test can't catch a missing `Discard`. There is no test for cancelling mid-conversion, and none for the 30 000 px width/height limits (only `Area`/`Disk` are exercised, at `:393-398`).
- **Fix:** Add a mid-conversion cancel test (large GIF to WebP is enough) and one test that a 30 001 px image is refused as "Image is too large."

### 8. NOTE: STATUS.md touches another WP's row
- Commit `1e9bf51` merges the duplicate WP-04 rows and marks WP-04 `DONE`. This matches reality (PR #4 is merged) and is probably welcome, but AGENTS §2.4 says not to edit other WPs' lines. Please state it in the PR. Not blocking.

## Review focus, in the requested order

1. **Format sniffing: PASS.** Both read paths pass an explicit `MagickReadSettings.Format` (`ImageConverter.cs:177-178` and `:197-204`). Formats come from the `ExtensionFormats` map (`:20-34`). An extension not in the map is refused as `Unsupported` (`:93-101`). Writes also pass explicit formats. Probe: SVG/MSL/MVG/text content named `.png`/`.jpg` all returned `CorruptInput` with 0 new files.
2. **Policy and limits: FAIL** (finding 1). They are applied once in the static constructor, before any read. The memory and size limits are set (`:263-265`) and the memory/area limit mapping works (test at `:385`). The policy takes effect for MVG only among the three I tried. The MVG test does not prove what it claims (finding 2).
3. **C1-C2: PASS.** `CreateTempPath` → `Commit` with `Discard` in `finally` when not committed (`:106-161`). The source is only read (`MagickImage(path, settings)`, no write mode), and a test hashes the source before and after. No `File.Delete/Move/Copy` in the converter. Output goes only through the writer.
4. **Error mapping and cancellation: PARTIAL** (findings 3, 5, 7). Corrupt, missing-delegate and resource-limit mapping are correct. Write failures are not. Work runs in `Task.Run(…, cancellationToken)` with `ThrowIfCancellationRequested` between steps, and `OperationCanceledException` is rethrown.
5. **ADR-010: PASS with a note** (finding 6). Magick.NET-Q8-AnyCPU 15.0.0 exists, is the newest release on NuGet (checked the index), and its nuspec says `Apache-2.0`. No AGPL or GPL-only package. The test packages (MIT, Apache-2.0) are recorded.
6. **Tests and user folders: PASS.** All tests use a fresh `wc-img-test-<guid>` folder under the OS temp path and delete it afterwards. No reference to `wc-test` or any user folder.
