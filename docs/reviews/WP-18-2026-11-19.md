## Findings

1. **BLOCKING: `.github/workflows/release.yml:108-110` and `THIRD-PARTY-NOTICES.md:18,45-47`. The nuspec-only approach doesn't meet the WP's licence requirement, and PdfPig's required NOTICE file isn't shipped.**
   - The WP says to ship "the new packages' licence/notice files". User test 10 expects "the new packages' licence files are there".
   - For PdfPig, `pdfpig.nuspec` contains only `<license type="expression">Apache-2.0</license>`. It has no copyright line and no licence text.
   - The upstream repo at the nuspec's commit `a7bb35662bbbf405efddad50aedc9bcdcf515afc` has a `LICENSE` (full Apache-2.0) **and a `NOTICES.txt`**. That file attributes the code derived from Apache PDFBox/FontBox (Copyright (c) 2002-2007 www.pdfbox.org), the Adobe Glyph List and the Zapf Dingbats Glyph List (Adobe Systems Incorporated).
   - Apache-2.0 §4(a) requires a copy of the licence, and §4(d) requires redistributing the NOTICE file. Neither is met by a nuspec plus a URL to the Apache text.
   - For OpenXml, upstream `LICENSE` at commit `3139fdfd27414548a41555f7848d5728f6e71a42` says "Copyright (c) .NET Foundation and Contributors". `THIRD-PARTY-NOTICES.md` names only "(c) Microsoft Corporation", which comes from the nuspec `<copyright>`. MIT requires the actual copyright notice to travel with the code.
   - Precedent: for bblanchon.PDFium, which also ships no texts, the upstream licence files were copied into `installer/licenses/pdfium/`, with their source and SHA-256 recorded (THIRD-PARTY-NOTICES §4).
   - **Minimal fix:**
     1. Copy PdfPig's `LICENSE` and `NOTICES.txt` from commit `a7bb356…` and Open-XML-SDK's `LICENSE` from commit `3139fdf…` into `installer/licenses/` (for example `installer/licenses/PdfPig-0.1.16/` and `installer/licenses/DocumentFormat.OpenXml-3.5.1/`).
     2. Record the source URL, commit and SHA-256 of each file in THIRD-PARTY-NOTICES.
     3. Stage the files in `release.yml` with the same `Test-Path`/throw guard, so a missing file fails the build. The nuspecs can stay.
     4. Correct the OpenXml copyright holder to ".NET Foundation and Contributors" (keep the nuspec line too). This covers DocumentFormat.OpenXml.Framework as well, since it comes from the same repo and commit.
     5. Close open question 7.
   - `installer/licenses/` is outside the Owns list, so the coordinator has to approve that (as for WP-12). Open-XML-SDK's `NOTICE` covers StyleCopAnalyzers, which is a build-time analyzer and probably not in the shipped DLL. Shipping it too is optional and harmless.
   - System.IO.Packaging is fine: its own `LICENSE.TXT` and `THIRD-PARTY-NOTICES.TXT` are shipped.

2. **BLOCKING: `src/WheelConvert.Converters.Docx/PdfTextExtractor.cs:65` (`gap > TextRules.ParagraphGapRatio * bodySize`). The paragraph regrouping splits ordinary 1.5-spaced and double-spaced text into one paragraph per line, and splits multi-line headings.**
   - Probe, 4 lines of 11 pt Helvetica:
     - Leading 13.2 gives 1 paragraph (correct).
     - Leading 16.5 (1.5 spacing) gives **4 paragraphs**.
     - Leading 22 (double spacing) gives **4 paragraphs**.
   - With the gap rule removed (style change only), DocstrumBoundingBoxes keeps all three cases as one block, so it's the regrouping that breaks req. 4 ("Join each block's lines into one paragraph").
   - A 2-line 28 pt title gives two `Heading1` paragraphs.
   - 1.5 spacing is common in reports and theses (user test 7).
   - Judgement on the decision itself: some regrouping is justified. Without it, test 1 fails because Docstrum merges the title and paragraphs into one block, as the builder said. The problem is the fixed threshold, measured against body size, not the line spacing used in each block.
   - **Fix:** make the split relative to each block's own line pitch. For example, start a new paragraph when a gap is more than about 1.5 × the block's median line gap (or the median baseline-to-baseline distance), and when the style class changes. Don't use a fixed multiple of the body size.
   - **Tests to add:** 1.5 and double spacing stay one paragraph; a 2-line heading stays one heading; the existing test 1 still gives Heading 1 + 3 paragraphs.

3. **BLOCKING (missing safety test, C2/S1): `src/WheelConvert.Converters.Docx/DocxConverter.cs:128`. The read-only/share-mode open is correct but no test covers it.**
   - Changing it to `FileAccess.ReadWrite` passes 28/28. Changing it to `FileShare.Read` also passes 28/28.
   - It can be tested: Converters.Pdf has `SourceOpenInAnotherApp_StillReadable` (`PdfConverterTests.cs:361`).
   - My probe confirms the current code converts while another handle holds the source open with `FileAccess.ReadWrite, FileShare.ReadWrite`.
   - **Fix:** add two tests:
     - The source is held open by another `FileStream(ReadWrite, FileShare.ReadWrite)` and the conversion succeeds. This catches `FileShare.Read`.
     - The source has the read-only attribute and the conversion succeeds, with the attribute cleared in cleanup. This catches `FileAccess.ReadWrite`.

4. **`DocxConverter.cs:65-68` (non-blocking): a locked or unreadable *source* is reported as "Couldn't save the file here." (`OutputFailed`).**
   - Probe: source held with `FileShare.None` gives `OutputFailed` "Couldn't save the file here.". The message points at the output, but the problem is reading the input.
   - The same applies to any `IOException` from `ReadPages`, because the inner catch at line 167 excludes `IOException`.
   - (A truncated PDF correctly gives `CorruptInput`.)
   - **Fix:** catch the `FileStream` open in `ReadPages` and map `IOException`/`UnauthorizedAccessException` there to a read-side message, such as "This PDF can't be opened. It may be in use by another program." Use `ConversionError.CorruptInput` or whichever code C1 lists for an unreadable source.

5. **`PdfTextExtractor.cs:37` (non-blocking): junk detection isn't covered end to end.**
   - Changing `junk++` to a no-op passes all tests. Only `RejectReason` and `IsJunk` are unit-tested.
   - **Fix:** add a converter-level test, either a PDF whose text extracts as PUA or U+FFFD, or a test seam over `PdfTextExtractor` counts. That checks the "Couldn't read the text in this PDF." path through `ConvertAsync`.

6. **`DocxConverter.cs:156` and `:106` (non-blocking): per-page cancellation and cancel-after-write aren't really tested.**
   - Removing the in-loop `ThrowIfCancellationRequested` still passes: the 200-page test reads every page, then throws at line 98.
   - Removing the post-write check also passes. `Cancel_DuringWrite_DiscardsTheTemp` cancels at progress 0.9, which trips line 98 *before* `CreateTempPath`, so it never exercises the discard path its name claims.
   - Discard-on-failure itself is covered: removing `Discard` fails `CommitFailure_IsOutputFailed_AndTempDiscarded`.
   - **Fix:**
     - In the 200-page test, assert that progress stopped early (for example, the maximum reported value < 0.5).
     - Rename the write test, or make it cancel from inside the writer.

7. **`DocxWriter.cs:58-59` (non-blocking): the heading style definitions aren't asserted.**
   - Renaming the styles-part ID `Heading1` to `H1` passes all tests, and `OpenXmlValidator` doesn't flag a `pStyle` with no matching style.
   - Without a matching definition, Word can't attach the heading to its navigation-pane outline from this file's styles.
   - **Fix:** in test 1, assert that the styles part has `Heading1`/`Heading2` with outline levels 0/1 and that every `pStyle` used resolves to a defined style.

8. **`PdfTextExtractor.cs:63` (non-blocking, a judgement call): headings are classified per line, not per block median as req. 5 words it.**
   - This follows from the regrouping and is reasonable. Once finding 2 is fixed, classify each regrouped paragraph by its own median size, so a heading line with a smaller first letter or symbol doesn't flip class.
   - Mention the deviation in the PR's "Decisions taken" section.

9. **Nits (non-blocking):**
   - `TextRules.cs:93,108` and `DocxConverterTests.cs:142-143` contain literal U+FFFD, U+FFFE, U+FFFF and U+E000 characters in source. They're invisible and fragile, so use `'�'`, `'￾'`, `'￿'`, `""`.
   - `IsJunk` misses supplementary-plane private-use characters (surrogate pairs, U+F0000+), since `GetUnicodeCategory(char)` returns `Surrogate`. That's minor.
   - `XmlSafe` is unit-tested, but removing its call in `PdfTextExtractor.Flush` passes all tests (no PDF with control characters).
